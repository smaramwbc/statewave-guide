# Indexer quality

The indexer makes claims about an application. This document defines how those claims are measured,
and where the current numbers come from.

> **Numbers in this document are generated by `pnpm test:indexer-quality`.** Do not edit them by
> hand. If a number here disagrees with the benchmark output, the benchmark is right.

## Why measure at all

A deterministic extractor can be wrong in two directions, and they are not equally bad.

**A false positive** is a relationship the graph asserts that is not true. It is the worse failure by
a wide margin. It will be shown to a user as a fact about their own application, it carries the
authority of static analysis, and nothing downstream is positioned to question it. Worse, it is
invisible: nobody reports a bug about a wrong edge they never looked at.

**A false negative** is a relationship the graph misses. It makes the guide less useful, but it is
honest, and — because the indexer emits a diagnostic wherever it declines to resolve something — it
is _observable_. A missing edge with a `UNRESOLVED_DYNAMIC_CALL` next to it is a work item. A wrong
edge is a liability.

So the target is **precision at or near 100%, with recall as high as we can get without spending
precision**. A relationship type whose precision drops below 100% is a bug to be fixed by _removing_
edges, not by tuning a threshold.

## Method

### Ground truth

`packages/indexer/test/fixtures/realistic-app/expectations.json` is a hand-written manifest of what a
careful indexer should find in the fixture application. It has four sections:

| Section              | Meaning                                                                          |
| -------------------- | -------------------------------------------------------------------------------- |
| `nodes`              | Nodes that must exist, by canonical id, with the file and line that justify them |
| `relationships`      | Edges that must exist, with the expected confidence and a written reason         |
| `expectedUnresolved` | Things the indexer must **fail** to resolve, and the diagnostic it must emit     |
| `mustNotExist`       | Edges that must **never** appear — the false-positive traps                      |

Every file and line reference in the manifest is verified against the real fixture source by a
checker script, so the ground truth cannot drift away from the code it describes.

### Metrics

For each node kind and each relationship type:

```
precision = |found ∩ expected| / |found|
recall    = |found ∩ expected| / |expected|
```

Plus two things a precision/recall table does not capture:

- **Trap violations** — how many `mustNotExist` entries the indexer emitted anyway. This number must
  be **zero**. It is not averaged into anything; a single violation is a failure.
- **Diagnostic coverage** — how many `expectedUnresolved` cases produced the diagnostic they should
  have. A case that resolved to nothing _and_ said nothing is counted as a miss, because silence and
  a considered refusal are different outcomes.

## Rules for changing these numbers

1. **Do not adjust the fixture to make a score go up.** The fixture exists to be hard. If a pattern
   in it is unrealistic, fix it because it is unrealistic — and say so in the commit.
2. **Do not add a relationship type to the manifest after the fact to match what the indexer
   happens to produce.** The manifest is written from the source, by reading it as a developer would.
3. **A precision regression blocks a change. A recall regression is a discussion.**
4. **A trap violation blocks a change, always.**

## Known limits of this measurement

- **One fixture.** Precision measured against a single application, however realistic, is precision
  against one team's habits. The real-world indexing report in
  [`docs/real-world-indexing-report.md`](real-world-indexing-report.md) is the counterweight: it runs
  the indexer over a production codebase where there is no ground truth, and reports what it found
  and what it could not resolve.
- **The manifest is written by the same people who wrote the extractors.** A pattern neither the
  fixture author nor the extractor author thought of is missing from both, and scores 100%.
- **Recall is measured against what we decided to look for.** A relationship type the graph does not
  model at all does not show up as a miss anywhere.

These are real limits and they are why the numbers are reported per relationship type rather than as
a single headline figure. An average would hide exactly the categories that are struggling.
